# BRT 360 — Intent CRM — Sprint 1 Implementation Plan

Companion engineering plan to `BRT360_Intent_CRM_HLD.docx`. This document covers **Sprint 1 (Weeks 1–2, C2M: INT-01/02/03)**, built as a real, working vertical slice through all six HLD layers. Sprints 2–4 extend the same skeleton without structural rework.

## 1. Stack decisions

| Concern | Choice | Why |
|---|---|---|
| Backend | Python 3.11, FastAPI, SQLAlchemy 2.0, Alembic | Async-first, OpenAPI-native (fits the TMF-contract-shaped adapters), strong typing via Pydantic |
| Frontend | React 18, Vite, TypeScript, Tailwind | Fast iteration, same mental model as your existing stack |
| Database | PostgreSQL (prod), SQLite (local dev default) | SQLAlchemy abstracts both; zero-setup local bootstrap, Postgres via `DATABASE_URL` for anything beyond a laptop |
| LLM | OpenAI API (`gpt-4o-mini` default, configurable) | Per your decision; a rule-based fallback classifier keeps the slice runnable with no API key during initial dev/test |
| Event bus (MVP) | Outbox pattern — `domain_events` table, polled/consumed in-process | HLD specifies Kafka-class for production; a DB-backed outbox is interface-compatible and lets Sprint 1 ship without standing up Kafka. Swapping to real Kafka later only touches `data_intelligence/event_bus.py`. |

## 3. Architecture-to-code mapping

Each HLD layer is a Python package, not a separately deployed service, for Sprint 1 — correct HLD layering with monolith deployment simplicity. Splitting into independently deployable services (per HLD §9.1) is a later-sprint infra concern, not a Sprint 1 blocker, and the package boundaries are already where a future service split would cut.

| HLD Layer | Package | Sprint 1 responsibility |
|---|---|---|
| Experience | `app/experience` | `POST /api/intents` — accepts free text, returns the full execution trace |
| Intent | `app/intent_engine` | `classifier.py` (NLU), `context_assembly.py`, `reasoning.py`, `verification.py` |
| Telecom CRM Core | `app/crm_core` | `catalog_service.py` — compatibility validation, PDC-style pricing, eligibility rules, versioned publish |
| Orchestration | `app/orchestration` | `orchestrator.py` — saga runner with idempotency keys and per-step compensation |
| Integration | `app/integration` | `tmf620_adapter.py` (internal, TMF620-shaped), `notification_adapter.py` (stub, logs + DB) |
| Data & Intelligence | `app/data_intelligence` | `event_bus.py` (outbox), `audit.py` (`IntentExecutionLog`) |

## 4. Design decision: deterministic orchestration steps, LLM for classification + rationale only

The HLD describes the Reasoning & Planning Engine as an LLM agent that "produces an ordered execution plan." For Sprint 1, the actual orchestration steps per intent are **deterministic and rule-based** (taken directly from HLD §7's Orchestration Steps for INT-01/02/03), not freely generated by the LLM at runtime. The LLM is used for:

1. **Classification** — free text → `{intent_type, entities}` (genuine NLU problem)
2. **Confidence + rationale** — a human-readable explanation of why this plan was chosen, with a confidence score

This is a deliberate divergence from a literal reading of §4.3, made for two reasons the HLD's own NFRs demand: **AI Governance** (§8.5 — every action must be explainable, which is far stronger when the steps are known-good and audited, not freshly invented per call) and **Reliability** (§8.4 — a telecom product catalog is not a safe place for an LLM to improvise a step sequence). The plan's *steps* are fixed per intent type; the LLM's job is recognizing *which* intent and *which* entities, which is exactly where NLU adds value and a keyword match would break on real phrasing.

## 5. Data model (Sprint 1 scope)

```
product_specifications   id, name, product_line, is_atomic, created_at
product_offerings        id, name, segment, status (draft/active/retired),
                          version, price, price_floor, effective_date, end_date,
                          parent_offering_id (self-FK, for versioning history)
price_plans              id, product_offering_id, list_price, discount_ceiling_pct
bundle_eligibility_rules id, product_offering_id, segment, channel, region
bundle_compatibility_rules
                          id, primary_product_line, addon_product_line, max_addons
intent_execution_log     id, intent_type, raw_text, entities_json, context_json,
                          plan_json, confidence, status, created_at, completed_at,
                          human_override_json (nullable)
domain_events             id, correlation_id (→ intent_execution_log.id), event_type,
                          payload_json, created_at
```

`intent_execution_log` + `domain_events` together are the Learning & Feedback Loop (HLD §4.6) and Observability backbone (§8.3) — every intent execution is fully reconstructable from these two tables.

## 6. INT-01/02/03 orchestration steps (as implemented)

Directly from HLD §7, made concrete:

**INT-01 — Launch a new bundle**
1. Validate composition against `bundle_compatibility_rules`
2. Compute price (list price − discount ceiling check against price floor)
3. Generate eligibility rules (segment/channel/region) from request entities
4. Publish `ProductOffering` as a new version (status=active)
5. Emit `offering.published` → notification stub to Sales/Care

**INT-02 — Modify a live bundle**
1. Impact analysis — identify this offering's current version
2. Validate change against grandfathering policy (existing version stays `active` for current subscribers; a new version is created rather than mutating in place)
3. Create new effective-dated version (`parent_offering_id` links to prior version)
4. Flag prior version `superseded`
5. Publish updated entry

**INT-03 — Retire a bundle**
1. Validate a replacement/migration path is specified (reject if not, per HLD §7's hard rule — "no retirement is permitted without a migration path")
2. Set end-date, status → `retired`
3. Emit `offering.retired` (stands in for the migration campaign trigger)
4. Retain full history (no deletes, ever — status + version only)

```
  }

GET /api/catalog                        # list current + historical ProductOfferings
GET /api/catalog/{id}/versions
GET /api/audit                          # IntentExecutionLog, most recent first
GET /api/audit/{id}                     # full trace for one execution
```

## 8. Testing approach

One pytest module per intent (`test_int01_launch_bundle.py` etc.), each asserting: the classifier resolves the right intent from a realistic free-text phrasing, the orchestrator executes all steps, the resulting `ProductOffering` is correct, and an `IntentExecutionLog` + matching `domain_events` rows exist. The rule-based classifier fallback is tested directly (no API key needed in CI); an OpenAI-backed test is marked to skip when `OPENAI_API_KEY` is unset.

## 9. What's deliberately deferred past Sprint 1

- Real TMF620/TMF637 calls to an external OSM/UIM/BRM system — stubbed behind the `integration/` adapters now, swapped later without touching `crm_core` or `orchestration`
- Kafka — the outbox table is consumed in-process; swapping the consumer to a real Kafka producer is isolated to `event_bus.py`
- RBAC/OAuth2 — Sprint 1 has no auth; required before any shared/multi-user environment
- Multi-tenancy — HLD Appendix B marks this optional for MVP; single-tenant by default
