# Cell-based tenancy: design for the largest tenants

Phase 5 of the architecture plan. This is a design for later, not something
built today: no tenant needs it yet. It records how BRT 360 would give a large
tenant (or a group of tenants) an installation of its own, so the decision is
quick when one does.

## What a cell is

A **cell** is one complete BRT 360 stack: every container in
`deploy/compose/docker-compose.yml`, with its own Postgres, Redis, workers,
monitoring and secrets, serving a fixed set of tenants. Today production is
cell 1 and holds every tenant. Staging already shows that two stacks run side by
side on one server without sharing anything (`COMPOSE_PROJECT_NAME`,
`IMAGE_PREFIX`, `WEB_PORT`).

Why cells rather than splitting further by domain:

- **Blast radius.** A runaway load, a bad migration or an outage in one cell
  touches only its tenants.
- **Noisy neighbours.** A tenant loading millions of BIM rows or running heavy
  analytics doesn't slow anyone else down.
- **Data residency and contracts.** A tenant that needs its data in a country,
  or on its own hardware, gets a cell there.
- **The same code everywhere.** A cell is the same release, so nothing forks.

## When a tenant gets its own cell

Any one of these, measured on the Services dashboard (Grafana, *BRT 360 -
Services*) and in the database:

| Signal | Threshold |
|---|---|
| The tenant's share of requests or AI tokens in its cell | over 40% for a month |
| The tenant's rows in the largest tables (orders, assets, events) | over 50% of the cell |
| A p95 target missed in its cell while the others are idle | repeatedly |
| A contract: residency, dedicated hardware, own maintenance windows | on signing |

## What has to change to run more than one cell

1. **Tenant directory.** It's a small global table, kept outside every cell:
   tenant slug → cell, plus cell → base URL. It's the only shared state.
2. **Routing.** Each tenant reaches its cell through a host name: either
   `<tenant>.brt360-tech.com` → the cell's front door (a DNS record per tenant),
   or one sign-in page that looks the email up in the directory and redirects. The
   host name is simpler and keeps every request inside one cell.
3. **Users.** Today an email is unique across the installation (`users.email`).
   With cells it's unique per cell, and the directory maps email → cell for the
   shared sign-in page. Platform admins sign in to each cell, which is no worse
   than now.
4. **BRT_IDs.** Codes must stay unique across cells, because BIM and integrations
   carry them between systems. Each cell gets its own range of the 40-bit
   sequence. It is set once in the cell's register (`brt_id_counter` starts at
   `cell_number << 34`), which leaves room for 64 cells of 17 billion records each.
   The code format doesn't change, and `issued()` keeps working per cell.
5. **Moving a tenant to a cell.** Every tenant row carries `tenant_id` (row-level
   security relies on it), so a tenant's data can be exported table by table:
   1. Run `pg_dump --data-only` restricted to `tenant_id = X` (generated by
      `app.rls.tenant_tables`), plus the shared reference rows it points to.
   2. Load it into the new cell's database. The rows keep their BRT_IDs.
   3. Switch the directory entry.
   4. Delete the rows from the old cell after a grace period.

   Integer ids collide between cells. The move renumbers them in the export, which
   is safe because everything outside the cell refers to records by BRT_ID.
6. **Deploys.** `deploy_docker.ps1` gains `-Cell N`. A release goes to staging,
   then to one cell (the canary), then to the rest.
7. **Monitoring.** Each cell's Prometheus gets a `cell` label, and one Grafana
   reads them all.

## What we already have that makes this cheap

- Every service is stateless; everything it needs is in Postgres and Redis.
- Every tenant row is marked with `tenant_id` and protected by row-level
  security. That's what makes a per-tenant export complete.
- BRT_IDs are the external identity of every record, so internal ids never leave
  a cell.
- A whole stack is defined in one Compose file and deployed by one script.

## Not decided yet

- Kubernetes before cells, or cells on Compose? A cell is the same unit either
  way. Moving to Kubernetes first makes a cell a namespace and a Helm release.
- Where the tenant directory lives: a small extra Postgres, or a managed key-value
  store.
- Billing per cell for dedicated cells.
